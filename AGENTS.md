## Conventions

- Session-authenticated backend actions: `authenticateSignShopSession` + `base44.asServiceRole.entities.*` in `base44/functions/*/entry.ts`.
- Idempotent creates: `createFoundationRecordWithRecovery` / `ensureIdempotentEntityCreate` with `creation_request_key`.
- Concurrency: `replaceFoundationFieldsIfUnchanged` / `replaceEstimateFieldsIfUnchanged` / `deleteBuilderEntityIfUnchanged` — CAS anchored on loaded `updated_date` + baseline fields.
- Frontend lists: `loadAllEntityRows` (paged, rate-limit retry, dedupe, fail-closed). Its `cacheTtlMs` TTL cache (≤30s cap) and in-flight dedupe are keyed per **entity object** + query/sort/limits — identical reads from different call sites share one slot, so pass `cacheTtlMs` consistently on hot shared reads (e.g. `staffEntities.AuthorizedEmail` roster). `primeEntityRowsCache(entity, query, sort, rows)` seeds that same per-entity slot after a `loadEntitiesBatch` read.
- Deploy a function: `npx base44@latest functions deploy <name> --app-id <id> --json` (deploys from LOCAL file — pull remote first). Site publishes only on explicit request.
- Publish the app: `sandbox checkpoint` → `POST /api/apps/{id}/app-checkpoints/{checkpoint_id}/retry-build` (waits for `"status":"ready"`) → `POST /api/apps/{id}/deploy` with `{"checkpoint_id":"..."}` (use `MSYS_NO_PATHCONV=1` on Windows; `api fetch` mangles paths otherwise). Deploying a bare `checkpoint_id` before its build is ready → 500 "Failed to load backend function source". `base44 deploy` (local) fails 428 if local entities are missing remote ones — prefer checkpoint deploys.
- `functions pull` writes a MALFORMED `"entry": "base44/functions/<name>/entry.ts"` into function.jsonc (correct: `"entry": "entry.ts"`); it breaks checkpoint builds. If a deploy fails `checkpoint_source_no_longer_compiles`, grep remote `base44/functions/*/function.jsonc` for `base44/functions/` and fix all hits.

## Function deploy gotchas (learned 2026-10-31)

- `functions deploy` uploads ALL `*.{js,ts,json,jsonc}` in the function dir + `base44/shared/` imports — not just `entry.ts`.
- `resolvePermittingAddress` AND `findLocalityByAddress` both serve `main.ts` (`function.jsonc` `"entry": "main.ts"`), a **generated bundle** — editing `entry.ts`/`handler.ts` alone never changes live behavior. Canonical source is `findLocalityByAddress/handler.ts`; regenerate with `node scripts/build-permitting-address-runtime.mjs`, then copy the output to BOTH `entry.ts` and `main.ts` in BOTH function dirs before deploying. `functions pull` writes the DEPLOYED (stale) `main.ts` into the local dir — always re-copy from a fresh regeneration after a pull.
- `functions deploy` updates ONLY the sandbox function runtime — the live site serves function code bundled into the published **checkpoint**. New function code is invisible at the live URL until `checkpoint → retry-build → POST /api/apps/{id}/deploy` ships it. (Env-var changes like secrets DO reach the live runtime without new code.) Verify what the live site runs by its `lookup_revision` marker, not by deploy success.
- `site deploy` archives the BUILD OUTPUT dir (`dist/`), not the repo — 50MB cap. `public/` gets copied into dist by Vite, so fat asset dirs (permitting-evidence ~71MB, fleet-assets ~67MB) blow the cap. Keep evidence blobs out of `public/` or host them in Base44 file storage. **This caused a production outage 2026-10-31**: partial upload published index.html referencing missing hashed assets → blank site. Fix going forward: use `npm run deploy:site` (build → `scripts/strip-site-deploy-assets.mjs` removes the fat dirs → `site deploy --no-build --publish`). Previously-uploaded copies keep serving from the retained asset store, so stripping does not break `/fleet-assets/*` or `/permitting-evidence/*` URLs.
- `sandbox write` on an existing file needs `--overwrite`; content comes via stdin (`cat file | npx base44 sandbox write <path> --overwrite`). `sandbox edit` matches `old_text` against STORED bytes — remote files are stored CRLF while `sandbox read` JSON-normalizes to LF, so build old_text/new_text with `\r\n` or the matcher 400s "old_text not found". Payload format is a bare JSON array `[{old_text,new_text}]` on stdin, not `{edits:[...]}`.
- `functions deploy` rotation is staggered per worker — fresh deploys can serve old code for tens of minutes (seen ~50min). Verify a new bundle is live via a response-shape marker (e.g. a new response field), not by retry timing. `functions deploy` updates the runtime only — sandbox source must be written separately or a future deploy regresses the fix.
- Silent-write debugging: `.catch(() => null)` on CAS write helpers hides conflict errors permanently. When a back-stamp doesn't land, temporarily surface the error into the response (matches `stage_sync_warning` pattern, e.g. `intake_link_warning`) — can't debug what you can't see.
- Rate limits: entity reads share `entity_list allows 140 requests per 60s for each caller` — the whole app's pollers drain one budget. `resolvePermittingAddress` now caches its PermitLocality/JurisdictionProfile catalogs (5min) + session auth (90s) in `handler.ts` so bursts don't multiply reads.
- Diagnose deployed-function behavior with `error_detail` on busy responses; if a response lacks a field the source has, the runtime is serving a stale generated bundle (`main.ts`), not your edited source.
- `boardFeed` uses server-side field projection (SDK `filter(q,sort,limit,skip,fields)`): allowlist lives in generated `base44/shared/boardFeedFields.ts` — rebuild with `node scripts/build-board-feed-fields.mjs` after ANY entity-schema change or FEEDABLE heavy-list change, then redeploy boardFeed. Undeclared stored fields (e.g. WorkOrder `_salesTaskAdoption`) are in `KNOWN_EXTRAS` in the generator — check live rows for extras before trusting a schema-only list.
- App-level cap: `App entity read traffic volume limit exceeded` is a whole-app rolling entity-read volume ceiling, distinct from the per-caller 140/60s — when it trips, every function's entity reads fail simultaneously. Verified contributors: sustained `resolvePermittingAddress` traffic (only LocalityPickerDialog + external scripts call it) and full-table pulls; the projection + 30s feed cache + delta cursors are the mitigations.
- `smartsheetSyncAction` WorkOrder reads use `syncPullFields(dataset, bindings)` (top of entry.ts): derived projection = mappable keys ∪ configured binding keys ∪ sync-meta ∪ audited side fields ∪ system. Extending it? Add any new `record.<field>` reads to `SYNC_PULL_SIDE_FIELDS` — a missed field silently verifies as unchanged/failed. Order pulls stay unprojected (all fields needed).
- Geocode chain in `findLocalityByAddress/handler.ts`: Google (10min REQUEST_DENIED cooldown, `geocode_diagnostic` always probes) → browser census_hint → OSM Nominatim (6s) → US Census (5s, last — worker often can't reach census.gov). `fixedJSON(url, timeoutMs)` accepts a per-call timeout.
- Local repo drifts behind the sandbox fast (builder works continuously): before `npm run build`, diff remote `package.json` + `find src -type f` against local — a stale local tree fails on missing deps/files, not your edits. `sandbox read` accepts MULTIPLE paths in one call — pull missing files in ~10-file chunks.
- Playwright waterfall: `.audit-work/waterfall.mjs /Page` needs `MSYS_NO_PATHCONV=1` on Git Bash (path args get mangled) and `playwright-core` matching `~/AppData/Local/ms-playwright/chromium-*` version.
- `sandbox write` has a **per-path circuit breaker**: repeated failed writes to the SAME path trip it — the path then 502s on every attempt while identical content writes instantly to any other path. Bypass: write to `<path>.mpnew` then `sandbox run "mv <path>.mpnew <path>"`. For <5KB payloads, `sandbox run "echo '<base64>' | base64 -d > path"` also works (sandbox run does NOT forward stdin — remote `base64 -d` hangs → 504; content must ride in the command arg, local Windows spawn limit ~8KB).
- `sandbox read` JSON shape is `{"files":[{"path","content"}]}` — never `j["content"]` at top level (wrote 0-byte files once). Remote content can contain lone surrogates — write with `errors='surrogateescape'`.

## File Bridge platform notes (learned 2026-11-02)

- **Sandbox ≠ production data plane**: `preview-sandbox--<id>.base44.app` functions read/write the SANDBOX entity store; `app.base44.com/api/apps/{id}/entities/*` and `base44 exec` hit PRODUCTION data. A row created via one is invisible to the other. Entity SCHEMAS also needed `POST /api/apps/{id}/entity-schemas {entity_name, entity_schema}` — writing `.jsonc` files does NOT provision them (verified: `FileBridgeHealth` 404 until API-created).
- **Entity jsonc MUST include top-level `"type":"object"`** or the schema API 400s.
- **GlobalSettings fields are `setting_key`/`setting_value`** — not key/value. Create is admin-RLS-restricted: neither entity API nor `base44 exec` can create rows; use a service-role function (`fileBridgeIngest bootstrap_settings` pattern).
- **Secrets**: `POST /api/apps/{id}/secrets {"NAME":"value"}` — write-only, redeploys functions. `FILEBRIDGE_HMAC_KEY` set this way (dev value in `.audit-work/fb-devkey.txt`, local only).
- **Function invoke URL**: `POST https://<host>/functions/<name>` — preview host `preview-sandbox--<id>.base44.app` (+`?preview_token=`); published host `clay-flow-signage-suite-387da97c.base44.app`.
- **Large-file push pattern**: `.audit-work/push-file.mjs` — base64 chunk appends to `/tmp` then `base64 -d` (6KB chunks, retry×4, md5 verify). Use EXACT tmp filename in the decode — never glob `/tmp/push-*.b64` (glob-decode once overwrote ingest with spike code; runtime served the corrupt bundle until next rotation).
- **Function rotation**: sandbox writes redeploy staggered per worker — verify new behavior by a response-shape marker, not retry timing. Workers also cache module-globals independently (60s settings cache caused transient `fileBridge disabled` on some calls right after bootstrap — by design, tolerable).
- **Measured caps**: function body ~89MB b64-JSON (96MB raw → 413) → 32MB chunks; SSE holds ≥55s with live events; `bulkCreate` exists (array return), `deleteMany` works, serial write ~91ms; `integrations.Core.UploadFile` works but NO storage delete API exists — uploaded bytes are permanent.
- **429-masking rule**: `.catch(()=>[])` on a settings/command read turns shared-budget 429s into FAKE permanent states (`disabled`, `unknown command`). Read-error paths must return `read_unavailable`/`settings_unavailable` 503 (retry:true) and serve last-good cached settings (≤10min), never normalize-empty-into-disabled.
- **Actors unusable pre-publish**: external connect → 403 "not been published" even after `actors deploy`; `createClientFromRequest` anonymous client lacks `.actors` entirely. File Bridge uses SSE `command_wait` as the wake channel instead.
